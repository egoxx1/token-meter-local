## 실제 재현한 누락

이전 파서 소스를 실행한 결과(`bug-before.json`):

| 조건/값 | 이전 | 수정 후 |
|---|---:|---:|
| 서로 다른 생성 호출 | 559 | 559 |
| 저장 이벤트 | **25** | **559** |
| 일반+캐시 입력 합계 | 3,342,576 | **74,740,000** |
| 전체 출력 | 13,576 | **304,000** |
| 누락된 호출 | **534** | **0 (해당 재현 사례)** |

535개 호출이 하나의 상위 ID를 공유하고, 나머지 24개는 별도 ID인 합성 사례입니다. 74,740,000/304,000은 보고서의 대략값에 맞춰 설정한 테스트 입력이지 사용자 DB의 원 단위 검증값이 아닙니다.

별도의 step 559개가 동일 호출을 반복 보고하는 실제 SQLite에서도 최종 559개를 유지합니다. 응답 ID 자체의 재사용, 상위 ID만 있고 호출 ID 없음, 순서 역전, 명시적 step 인덱스, 늦게 붙는 응답 ID, 재시도, 잘못된 protobuf/메타데이터 한도도 검사했습니다.

## 복구·보존·경계 검증

기존 25개 장부를 실제 파일로 만든 뒤 559개로 수리했습니다. 원본 장부 백업, 구 ID 퇴역 수정본, 새 ID 보존, 변경 없는 재스캔에서 revision 불증가, 재시작 및 비-epoch 장부 삭제 후 journal replay를 검사했습니다.

초기화 경계가 처음 200개 뒤에 있는 합성 사례는 **원본 559개 / 활성 359개**로 유지됩니다. 재수집·재시작·source 보기로도 과거 200개가 활성 총량에 다시 들어가지 않습니다. 이후 전체 초기화를 수행하고 새 1,100토큰만 반영되는 것도 확인했습니다.

같은 구 호출이 새 호출 하나에 유일하게 대응하는 진행 중 기준점에서는 입력 +4,000, 출력 +600을 유지했습니다. 수백 호출이 이미 합쳐진 기준점은 호출 시각으로 재구성하며 과거 중간 카운터 손실을 경고합니다.

보존 로그에 퇴역 수정본만 저장하고 의도적으로 실패시킨 뒤 재시작하는 시험을 **일반 장부와 reset epoch 각각** 수행했습니다. 복구 계획이 사라지지 않고 새 ID들이 재구성됩니다. 원본이 없거나 원본 파싱 오류가 있으면 기존 장부를 허위 0으로 덮지 않습니다.

종료 측정은 byte-equivalent로 보존하고, 구버전 Antigravity 결과라는 경고만 표시합니다. 진행 중 측정과 특정 세션 측정은 다른 세션의 토큰을 섞지 않습니다.

## 독립성과 UI의 한계

Python `verify-antigravity.py`는 JS 파서/alias와 별도로 protobuf를 읽고 primary+retry 행을 순회합니다. 559개, 입력 74,740,000, 출력 304,000을 확인했습니다. 무작위로 상위 ID를 재사용하는 20×80개의 작은 사례도 토큰 보존식을 만족했습니다.

같은 비공개 필드 배치를 가정하는 두 구현의 일치는 공식 필드 의미를 검증하지 못합니다. 앱의 `DB ↔ 장부 대조`도 같은 JS 파서로 다시 읽는 구조 비교이며 독립적인 청구 검증이 아닙니다. 미지원 DB 의미는 테스트 수로 해결되지 않습니다.

브라우저 정상 URL 탐색을 시도했으나 `ERR_BLOCKED_BY_ADMINISTRATOR`가 발생했습니다. 정책은 변경하지 않았습니다. 이후 실제 앱 HTML/CSS/JS를 about:blank에 로드하고 테스트용 fetch bridge로 실제 인증된 루프백 API를 호출했습니다. 정상 탐색/CSP까지 통과한 종단간 테스트가 아닙니다. 서버의 인증·Host·Origin 검사는 별도 실제 HTTP 테스트에 있습니다.

새 UI는 초기화 시각/포함 도구/입력 전체 표시, 원본/활성 세션 전환, DB 대조, 정확값·축약 CLI 수치 대조, 안전한 JSON 다운로드, 세션 측정·고정을 시험했습니다. 375/768/1440px 제어 배치와 데스크톱 대조표의 차이 열 가시성도 확인했습니다. 모든 스크린샷은 합성 데이터입니다.

## 자원 사용 시험 — 숨기지 않는 한계

2만 primary + 2만 중복 step(메타데이터 4만 행)을 만들고, WAL에 5개를 더 쓴 뒤 재시작했습니다. 최종 **20,005개**가 남고 입력 **2,220,595,010**, 출력 **10,002,500**이 기대값과 일치했습니다.

한 번의 이 환경 시험에서 초기 읽기/저장 약 9.45초, 변경 없는 후속 검사 약 6.05초, WAL 증가 재수집 약 6.02초, 재시작+검사 약 11.42초였습니다. **최대 RSS 약 1.64GiB, ledger 약 94MB**였습니다. 이 최고치는 같은 Node 프로세스에서 새 Collector 객체를 만드는 재시작 시나리오를 포함하므로, 정상 단일 수집기의 고정 메모리량으로 해석하지 않습니다. GC와 기기 상태의 영향을 받으며 속도 SLA가 아닙니다. 수십만/수백만 요청 또는 저사양 장치에 적합한 경량 DB로 완료했다는 주장은 하지 않습니다.

큰 scan/save 뒤 자동 대기 간격을 늘리는 동작은 별도 단위시험을 통과했습니다. 이는 연속 CPU 부하를 줄이지만 전체 JSON 저장소의 메모리 한계를 해결하지 않습니다.

## 패키지 및 미검증 범위

VSIX/ZIP CRC, manifest XML·버전·확장 식별자·진입점·새 모듈·SQLite fallback 포함, source ZIP 추출 후 실행을 검사합니다. 실제 VS Code Extension Host 설치를 수행했다는 뜻은 아닙니다.

여전히 미검증: 사용자 원본 DB와 최신 CLI 상태바의 동일 시점 대조, macOS/Windows/WSL/SSH 실기, 실제 구독/청구액, Antigravity 모든 버전의 필드 의미, 구형 `.pb`, OS 네이티브 최상위 창, 장기 상시 실행과 디스크 고장, 운영 자동 배포/Marketplace.

완전한 사용자 실기 판정을 위해서는 설치한 기기에서 같은 세션·같은 범위를 골라 제공된 대조 기능을 실행해야 합니다. 진단 JSON은 경로·본문·접근키를 제외하지만 모델·시간·사용량 메타데이터를 포함합니다.
