# Token Meter Local 0.10.2 — 메모리 최적화 및 실측

기준: 사용자가 올린 `token-meter-local-0.10.1-all-files.zip` 안의 소스. 원본은 별도로 보관한 채 변경했습니다. 날짜: 2026-09-27.

## 수정 전후 측정

**같은 구조의 합성 데이터 20,000개 호출**을 사용했습니다. 실제 임시 SQLite DB에 생성 행 20,000개와 같은 호출을 가리키는 단계 행 20,000개를 넣었습니다. 최종 호출 수는 40,000이 아니라 **20,000**이어야 합니다.

| 작업 | 업로드된 0.10.1 최대 RSS | 0.10.2 최대 RSS | 감소율 | 전체 실행 시간 전 / 후 |
|---|---:|---:|---:|---:|
| 최초 수집 + 저장 | 844.1 MiB | **413.6 MiB** | **51.0%** | 6.88 / 7.20초 |
| 재시작 + 변경 없는 스캔 5회 | 532.7 MiB | **165.3 MiB** | **69.0%** | 4.33 / 5.37초 |
| 상태바 HTTP 조회 12회 | 659.4 MiB | **182.2 MiB** | **72.4%** | 25.04 / 5.24초 |
| 전체 사용 이력 JSONL 내보내기 | 2,064.7 MiB | **201.9 MiB** | **90.2%** | 9.22 / 9.10초 |
| 전체 초기화 + 재스캔 + 새 요청 | 1,381.9 MiB | **288.7 MiB** | **79.1%** | 9.12 / 9.19초 |

- Linux / Node.js 22.16.0 / 내장 SQLite. `process.resourceUsage().maxRSS`의 KiB를 1024로 나눈 **MiB**입니다. `/usr/bin/time -v` 원문도 동봉합니다.
- 작업마다 **새 프로세스를 시작**했습니다. 이전 Collector 객체를 같은 프로세스에 남겨 둔 채 '재시작'이라고 측정하지 않았습니다.
- 수집기 Node 프로세스와 같은 프로세스 안의 worker 메모리입니다. **VS Code 전체, 브라우저, Python fallback의 별도 프로세스, OS 파일 캐시는 이 수치에 합산되지 않습니다.** Fixture 생성 프로세스도 측정에서 제외했습니다.
- `--expose-gc`, 강제 GC, 메모리 제한 변경, 기록 샘플링·삭제·조회 건수 축소 없이 측정했습니다. 매 작업에 호출 수·입출력 합계 assertion을 넣었습니다.
- 비용 계산·토큰 의미·사용자의 단가 데이터는 유지했습니다. 계정 API 호출과 사용자 원본 DB 접근은 하지 않았습니다.
- 수치는 이번 환경의 단일 비교 실행 결과입니다. 반복 실행·운영체제·디스크·실제 데이터에 따라 달라집니다. RAM 절약과 실행 시간 단축이 같은 것은 아닙니다. 스트리밍 파싱의 비용 때문에 **재시작 시간이 오히려 늘어난 구간**도 있으며 이를 표에 그대로 기재했습니다.

## 집계 보존

초기화 전 각 작업의 호출 수 **20,000**, 입력 전체 **2,219,990,000**, 전체 출력 **10,000,000**이 전후 동일합니다. 일반 입력/캐시/THINKING이 각각 중복 없이 기존 총량에 포함되는 회귀 테스트도 유지했습니다.

전체 이력 내보내기 응답은 전후 모두 **300,090,444바이트 / 20,000줄**입니다. 큰 기록을 버리거나 첫 페이지로 자른 결과가 아닙니다. 바이트 수 일치와 합계 검사는 검증한 것이지만, 현재 시각 등의 메타데이터가 달라 전체 JSONL 파일의 SHA-256이 같다고 주장하지는 않습니다.

초기화 시험은 20,000개 기존 호출을 제외하고, 이후 **입력 1,000 + 출력 100 = 1,100토큰**인 새 요청 하나만 활성 장부에 남깁니다. 원본 관측 20,001개는 유지됩니다. 변경 없는 재스캔에서는 과거 토큰과 revision 로그가 증가하지 않습니다.

## 발견한 원인과 변경

| 원인 | 변경 |
|---|---|
| 장부와 journal 최신 인덱스가 같은 이벤트 객체 내용을 중복 보관 | journal 인덱스는 ID·순번·수정번호·해시·퇴역 상태만 보관. 필요한 내용은 스트림으로 재생 |
| 저장 요청 시 장부 전체 `structuredClone`과 거대한 JSON 문자열 생성 | 저장 큐의 실행 시점에 스냅샷 준비, 이벤트별 스트리밍 JSON 쓰기·fsync·원자 교체 |
| 시작 시 전체 JSON 문자열과 파싱 결과를 동시에 보유 | 기존 JSON 형식을 바꾸지 않고 이벤트 배열을 순차 파싱 |
| 동일 단가·출처·매칭 근거를 요청마다 중복 보관 | 정확히 같은 불변 메타데이터를 제한된 공유 풀로 재사용. 모델/공급자/모드/날짜 조건을 유지 |
| 초기화 이후 변경 없는 원본도 다시 계산·저장 | 원본 관측이 바뀐 경우에만 활성 증가분 재계산 |
| 상태바가 상세 대시보드 전체 데이터를 주기적으로 요청 | 경량 상태바 응답, 작은 버전 확인 ping, 조회 결과의 짧은 제한 캐시 |
| 전체 내보내기에서 모든 상세 객체와 문자열을 한꺼번에 생성 | 요청별 직렬화, HTTP backpressure를 적용한 스트리밍 |
| Python BLOB 한 줄을 작은 조각마다 계속 복사 | 제한을 검사하며 조각을 모아 완성된 줄에서 한 번 결합 |
| worker 결과 대량 복제 및 종료 전 다음 작업 진행 | 128개 단위 전송·확인 응답, worker 종료 확인 후 다음 수집 |
| 변하지 않은 부분 수집 DB를 매번 비싸게 재분석 | 완료한 동일 파일 상태는 재사용하되 경고 유지. DB/WAL 변화·수동 재분석·복구 필요 세션은 다시 읽음 |

`src/parsers.js`, `src/pricing.js`, `src/identity-repair.js`, `src/antigravity-sqlite.py`, `data/prices.extra.json`의 수정 전후 SHA-256이 같습니다. Antigravity protobuf 파일에서는 임시 객체 복제 방식을 줄였으며, 호출 식별·재시도 중복 병합 규칙은 유지했습니다.

## 추가로 수정한 실제 오류

journal에 저장할 필드를 선별하는 과정에서 `accountingVersion`, `usageSourceKind`, `usageObservedAt`이 빠졌습니다. 초기화·journal 복구 뒤 정상 기록을 구버전 accounting으로 판단할 수 있었습니다. 이 필드를 보존하도록 고쳤습니다. 20,000개 초기화 시험에서 원본 버전은 `unrepairedAccountingRecords = 20000`, 수정본은 `0`입니다.

이 경고를 숨긴 것이 아닙니다. **진짜 미복구 세션은 캐시와 무관하게 다시 읽고**, 불일치·읽기 오류는 계속 표시합니다. 현재 사용자의 '점검 필요'가 반드시 이 경로에서 발생했다고 확정한 것은 아닙니다.

## 화면과 내보내기

- `수집 검증 · 세션 비교`에서 **수집기 RAM(MiB), 활성/원본 기록 수, 저장 대기**를 볼 수 있습니다. 상태바 툴팁에도 RAM을 표시합니다.
- 동일 화면 요청이 겹치지 않도록 했습니다. 사용자가 연속 새로고침을 요청해도 하나씩 합쳐 처리합니다.
- 보이지 않는 브라우저 탭의 자동 화면 조회는 쉬고, 다시 보이면 갱신합니다. **수집기나 사용 로그 저장은 중단하지 않습니다.** PiP가 열려 있으면 갱신을 유지합니다.
- 지원 브라우저에서 사용자가 파일 저장을 허용하면 내보내기 응답을 파일에 직접 스트리밍합니다. 지원하지 않는 환경은 기존 Blob 다운로드를 사용하므로 **브라우저 쪽의 큰 파일 메모리 문제는 남을 수 있습니다.** OS 파일 선택 창은 모의 객체로만 시험했고 실제 환경에서의 허용 여부는 미검증입니다.

## 캐시 한계 / 데이터 보존

파생 조회 캐시는 최대 4개·직렬화 크기 합계 8MiB·최대 TTL 60초로 제한합니다. **8MiB는 직렬화 크기를 기준으로 한 한도이지 실제 JS heap의 엄격한 상한이 아닙니다.** 가격 공유 풀도 최대 4,096개입니다. 새 사용량·설정·측정·epoch 변경 시 다시 계산하고, 수집 경고는 캐시와 별도로 최신 상태를 붙입니다.

캐시에서 지우는 것은 다시 만들 수 있는 화면 결과뿐입니다. **장부·월별 사용 이력·백업·종료된 측정을 자동 삭제하지 않습니다.** 파일 형식과 데이터 폴더를 유지하며 이번 변경에 파괴적 이관/자동 초기화는 없습니다.

## 반복 조회 시험

20,000개 호출을 유지한 상태에서 인증된 상태바 HTTP 조회 **600회**를 연속 실행했습니다. 최대 RSS **198.5MiB**, 초기 로딩을 포함한 전체 경과 약 **6.12초**, 완료 후 호출 수와 journal 기록 수 모두 **20,000**입니다.

이는 짧은 스트레스 시험이지 24시간 장기 내구성 시험이 아닙니다. 메모리 누수가 전혀 없다는 증명이나 macOS에서 동일한 숫자가 나온다는 보장이 아닙니다.

## 재현 방법

소스 루트에서 실행합니다. 실제 사용 경로를 지정하지 않는 합성 전용 도구입니다. Node 내장 SQLite가 필요하며 fixture를 준비할 때 전체 원본 테스트용 기록을 생성합니다.

```sh
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase prepare --count 20000
# 출력한 base 경로를 아래 FIXTURE에 사용. 단계마다 별도 프로세스.
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase cold --fixture FIXTURE
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase steady --fixture FIXTURE
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase views --fixture FIXTURE
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase export --fixture FIXTURE
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase views --polls 600 --fixture FIXTURE
# fixture의 활성 데이터를 바꾸므로 reset은 마지막에 실행
node scripts/memory-benchmark.js --source /absolute/path/to/source --phase reset --fixture FIXTURE
```

이전 코드 비교에도 **같은 새 benchmark 스크립트**를 실행하고 `--source`만 업로드된 0.10.1 소스로 지정했습니다. 양쪽 모두 같은 count·fixture 생성 방식이며, 다른 디렉터리의 격리 데이터로 수행했습니다.

## 아직 남은 한계

전체 이벤트와 초기화 원본 관측은 Map으로 유지됩니다. **중앙 저장소를 SQLite로 전환한 버전이 아닙니다.** 장부 전체 저장, 거대한 측정 기준점, 전 범위 검색·정렬의 일부 비용은 기록 수에 비례합니다. 수백만 호출·여러 기기의 장기 운영, 실제 VS Code/Windows/macOS, 실제 사용자 DB·계정·청구서, 네이티브 PiP 동작은 별도 검증 대상입니다.

대형 첫 수집이나 복구는 여전히 평상시보다 RAM을 많이 씁니다. 메모리 제한만 낮춰 프로세스가 죽게 만들거나, 기록을 버려서 수치를 낮추는 방식을 사용하지 않았습니다. 읽기 한도를 넘거나 저장이 실패하면 오류를 유지합니다.
